## Binding product direction

SENTINEL is no longer represented adequately by a bulky S/radar/shield **as its future primary brand concept**. Its intended product identity spans player intelligence, game assistance, controlled/opt-in permitted execution, PvE/PvP, character builds, economy, quests, Companion/Launcher/Overlay, Web and security. Create credible identity studies **beyond recoloring the existing S**. Avoid naive joystick/sword imagery, cheats aesthetics, pixelated assets, scanner/HUD decoration, and indiscriminate generic SaaS/AI gradients. Current installed brand art, production v3 tokens and native apps remain unchanged until a replacement has been visually accepted, safely migrated and tested. **Retiring the old creative direction is not approval to delete the currently shipped asset.**

The Owner explicitly **deferred color-selection and final style approval**. The previous five palette boards are an entry point only, not product-wide mature designs. Evaluate richer identities and adapt their skins after component, interaction, information architecture and icon quality reach reviewable depth. Do not request visual acceptance of only palettes or unclickable flat page strips.

## Architecture and real-page requirement

The public website must have individually authored, addressable, navigable pages—not one vertical poster with anchor-like tabs. Navigation, contextual links, header, footer, breadcrumbs where useful, back/history, responsive layout, page-specific hero/body/illustrations and honest product-availability CTAs need their own design. The authenticated Web Control is a **separate product** with login, access control, security, devices, games, subscriptions, settings, diagnostics and isolated admin. Android, packaged Windows Launcher/Companion and Overlay each need platform-specific native hierarchy and behavior. Screens must account for the real source's implemented capability, exact platform/game version and supported run state.

### Components and interactions before decorative polish

Every recurring control has a reusable editable component and state vocabulary: `default / hover / pressed / focus-visible / selected / disabled / loading / progress / skeleton / empty / success / warning / error / offline / timeout / stale / unknown / unavailable / denied / revoked / stopped`. Declare input, data provenance, transitions, back/escape behavior, error recovery, Stop, responsive priority and screen-reader labels. Prototype several end-to-end flows instead of creating static frames only. Pixel-perfect pictures are not a replacement for editable vectors/text and interaction linkage.

### Brand/icon quality gate

Study 3–5 genuinely distinct symbols that can imply **intelligence + player assistance + controlled action**, including a restrained monochrome simplification. Construct one optical family of icons for app navigation, game modules, PvE/PvP, battle/automation, auction/trade/professions/quests, status/privacy/devices, voice, updates, diagnostic and emergency Stop. Match optical centers and stroke weight at 16/20/24/32/48 px; test Android adaptive masks, monochrome/themed icon, notification, splash, Windows app/installer/tray and favicon contexts. Production switch remains gated on explicit Owner selection plus measured native optical acceptance.

### Semantics and readiness honesty

Use `FACT / INFERENCE / RECOMMENDATION`, source and freshness, `UNKNOWN / UNAVAILABLE / UNVERIFIED / STOPPED`. Mark future assistant modes as **planned** when not implemented. `AUTOMATIC_EXECUTION_DISABLED` remains in effect: designed control states must not activate automated gameplay, bypass anti-cheat, remove operator terms/consent/entitlement/Policy/Action Gateway/Stop checks, imply private WoW L3 is verified, or fabricate Android captured data. Preserve current media-capture consent behavior, fail-closed security, exact-game-version capability and public download truth. No live deployment/signing/release.

## Process and Owner gate

1. Read live protected main at exact SHA and only relevant active/scoped contracts; inventory actual routes/assets/screens once. Reuse the existing Figma study and produce a **separate layered, reusable, interactive H design library/prototype** rather than importing lab screenshots.
2. Build H1/H2 identity families and cross-platform icon rules **alongside** H3–H5 reusable foundations/components/navigation, then design a complete reusable content architecture for H6–H10. A coherent vertical delivery must include H11 checks.
3. Provide realistic clickable flows and representative **fully detailed** screens in RU/EN, meaningful page-specific site assets and light/dark/high-contrast as appropriate. Include route maps, component inventory, states, animation timing and source-linked accessibility review.
4. Record exact Figma file/node references, screenshots and test evidence. Native product implementation should not be falsely claimed by a Figma prototype. Propose unresolved adjustments without choosing a production look.
5. **Stop for Owner only when a genuine final visual direction/brand selection is required.** Until then, refine independently and keep production v3. After selection, translate natively to B/C/D/E and require runnable/browser/host/physical acceptance.

**Definition of done for this design stage:** An Owner can navigate separate, realistic product flows, assess all logo/icon sizes and detailed controls, compare the same product journeys across platforms and decide on one coherent brand system. Passing token contrast alone, having 40 static screens, or showing six pretty palette cards is **not** sufficient.
