# Separate migration and runtime database authority

Production serving requires `SENTINEL_REQUIRE_RESTRICTED_DATABASE_ROLE=true`.
Staging can enable the same guard after native credential provisioning. The
runtime engine checks effective privileges at every transaction before enabling
the transaction-local service GUC. It rejects superuser/BYPASSRLS, database/role
creation, replication, any role membership, owned application relations or
databases, and effective database/public-schema CREATE privileges. Invalid flag
values fail closed. No DSN is emitted by the guard.

`migrate.py` prefers provider-native `DATABASE_MIGRATION_URL`, retaining
`DATABASE_URL` fallback for existing development and untransitioned staging.
The serving entrypoint removes the migration credential from its environment
before importing the application or provider SDKs. The existing Render command
`cd server && python migrate.py && uvicorn app.entrypoint:app ...` continues to
work; no second migration pipeline is introduced.

This reduces accidental runtime SQL authority. It is not process/host isolation:
the same provider startup environment supplies the migration subprocess. A
production migration runner with separate identity/custody remains a deployment
prerequisite; do not claim resistance to host compromise from environment removal.
The trusted Core service GUC intentionally permits service operations; application
principal/device authorization remains required and is not replaced by RLS.

database `sentinel`: all sixteen migration checksums match source; all 39 runtime

cryptographically random password inside PostgreSQL without secret input/output;
native rotation then succeeded. No plaintext credential was placed in SQL input,
chat, source, logs or files. Restricted table/sequence grants and owner default
privileges are prepared; migration metadata remains SELECT-only. Effective
database/public-schema CREATE privileges are false. The role remains NOLOGIN and
unused until the reviewed source is deployed and the native env transition runs.
No existing application credential or connection configuration was changed at
this preparation checkpoint.

## Concrete transition sequence

1. Issue a high-entropy password to the restricted SQL role using an approved
   secure credential runner that transmits secrets directly to PostgreSQL and
   Render's native secret store. Never type credentials into chat, source, issues,
   Drive documents, diagnostic output, SQL editor history, or shell arguments.
   For a SQL role with no initial password, a server-side generated bootstrap
   enables the native rotation API; generated bytes never leave PostgreSQL until
   the native custody transfer. Do not restore BYPASSRLS to make an API accept it.
2. Grant CONNECT on `sentinel`, USAGE on `public`, and SELECT/INSERT/UPDATE/DELETE
   only on application tables; grant sequence USAGE/SELECT where needed.
   `schema_migrations` is SELECT-only. No TRUNCATE, schema/database CREATE,
   relation ownership or role memberships. Apply equivalent owner default
   privileges for future application tables/sequences and verify the metadata
   table remains read-only after each migration. Preserve all FORCE RLS policies.
3. Put the owner URL in native `DATABASE_MIGRATION_URL` and restricted pooled URL
   in native `DATABASE_URL`; set the guard flag true in the same provider update.
   Retain TLS/channel-binding settings. Do not read/export unrelated env secrets.
4. Deploy existing staging from an exact protected-main SHA. Verify `/healthz`,
   all migration checksums, observed connection role, blocked DDL, MFA/device/
   session/recovery flows, and maintenance. Re-run source-bound staging smoke.
   A healthy process using an unknown role is not sufficient evidence.
5. If migration/grant/guard checks fail, keep traffic stopped for that generation;
   repair custody/grants or return to the previously verified staging configuration
   with an explicit recorded limitation. Production never disables the guard.

The Owner's production credentials/database/recovery approval remains separate.
No production service, key, database reset, or RLS weakening is authorized here.
